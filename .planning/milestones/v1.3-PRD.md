# PRD: Counterflux v1.3 — Brew with the Familiar

## Overview

**Product Name:** Counterflux — The Aetheric Archive
**Codename:** Brew with the Familiar
**Live URL:** [counterflux.vercel.app](https://counterflux.vercel.app)
**Version:** 1.3 (AI-powered deck generation, upgrades, and power-level retuning)
**Author:** James Arnall
**Status:** Draft — milestone scoping
**Last Updated:** June 2026

### Problem Statement

Commander deck-building is the most labour-intensive part of MTG and the least-served by software. EDHREC gives you popularity data, Moxfield gives you list management, Archidekt gives you analytics — none of them actually build a deck. The closest thing is EDHREC's "average deck" auto-fill, which is consistently mediocre because it ignores collection, ignores power level, and slots cards by frequency rather than role. The actual work — pick 99 cards from ~30,000, balance ramp/draw/removal/win-cons against budget/collection/power-level, tune for the specific table you're playing tonight — still happens in James's head. Even with EDHREC's top synergies pre-filtered, slotting them into roles and tuning for a Casual pod versus an Optimized cube is a multi-hour exercise.

Counterflux v1.2 unified collection + deck + intel into one surface, but the actual brewing still happens manually. v1.3 makes Mila do it.

### Goal

Add an AI-powered brewing layer to Thousand-Year Storm that uses Claude as the reasoning engine and EDHREC as the deterministic candidate source. Three brewing modes ship in v1.3 — build from commander, fill missing slots in an existing deck, and retune for a target power level. A fourth mode runs as a daily background cron — detects new-card releases against existing decks and surfaces upgrade recommendations on the Dashboard, notification bell, and Preordain. EDHREC supplies the candidate pool so Claude can't hallucinate cards that don't exist; Claude supplies the slotting, reasoning, and natural-language explanation that makes the suggestions trustable rather than just popular.

### Success Metrics

- **Brewing adoption:** James builds >= 1 deck end-to-end purely via the AI brewing flow within the first 30 days of v1.3 ship (binary — proves the loop works)
- **Suggestion quality:** >= 60% of AI-suggested cards accepted on first review pass per brew session
- **Brew speed:** median time from commander-selected to 99-card-deck-committed < 8 minutes (versus the current 2-4 hour manual exercise)
- **Cost per brew:** daily cost per active user < $0.50 USD with prompt-caching engaged
- **Cache effectiveness:** response cache hit rate > 40% after the first week of use
- **Reliability:** /api/deckgen timeouts or 5xx < 2% of generation attempts
- **Upgrade engagement:** James reviews >= 70% of upgrade recommendations within 7 days of them landing in the notification bell

### Request Flow (Phase 18 brew, happy path)

```
User clicks "Brew with AI" on Thousand-Year Storm
  → Brew modal opens; user sets power=4, collection-only=true, mode='build'
  → Modal submits to deckgen-store.requestBrew(payload)
  → deckgen-service.js hashes the request (commander_id, power, collection-hash, mode, archetype)
  → Cache check: db.deckgen_cache.get(hash) — if hit AND fresh (< 7d TTL), use cached response, skip API
  → On miss: POST /api/deckgen with Supabase JWT in Authorization header
  → Server: _origin-guard.js rejects non-counterflux origins
  → Server: validates JWT, fetches user.id
  → Server: profile.deckgen_generations_today check — 429 if >= 20
  → Server: getCommanderSynergies(commander) — reuses existing EDHREC integration, cached
  → Server: if collection-only, queries counterflux.collection with user JWT, intersects with synergies
  → Server: builds candidate pool (max ~200 cards) — Claude only sees these scryfall_ids + names
  → Server: anthropic.messages.create() with system prompt cached + user prompt
  → Server: parses Claude's structured JSON response, validates each scryfall_id exists in pool
  → Server: writes hash → response to counterflux.deckgen_cache (mirrored to Dexie on client receipt)
  → Server: increments profile.deckgen_generations_today
  → Server: returns 200 with { recommended: [...], budget_remaining: 19 }
  → Client: deckgen-store.brewResponse = response, opens review screen
  → User approves 87/99, rejects 12, clicks "Add approved"
  → Client: db.transaction('rw', db.deck_cards, async () => { ... }) — atomic commit
  → Single undo entry pushed to undo store
  → Toast "Added 87 cards to Breya, Etherium Shaper deck"
```

### Auth & Roles

No new auth surface. v1.3 reuses the existing v1.1 Phase 10 Supabase Auth with PKCE flow. The `/api/deckgen` endpoint requires a valid user JWT in the `Authorization: Bearer` header — same pattern as future authenticated endpoints would use. The Vercel Cron job (Phase 19) does NOT have a user JWT; it uses `SUPABASE_SERVICE_ROLE_KEY` to scan all users' decks server-side. This is the ONE exception to the "no service-role" rule established in v1.0–v1.2 — explicitly documented because the cron runs without a user context.

### Anthropic SDK Pattern

```js
// api/deckgen.js (excerpt — Phase 17)
import Anthropic from '@anthropic-ai/sdk';
import { checkRequest } from './_origin-guard.js';

const client = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

const SYSTEM_PROMPT = `You are Mila, Counterflux's deck-brewing familiar.

[stable text — role buckets, power-level rubric, output schema, response format]
[~3000 tokens of stable instructions — qualifies for prompt-caching]`;

export default async function handler(req, res) {
  const guard = checkRequest(req);
  if (!guard.ok) return res.status(guard.status).json(guard.body);

  const userId = await verifyJWT(req);
  if (!userId) return res.status(401).json({ error: 'unauthenticated' });

  await assertBudget(userId);                              // 429 if exceeded

  const { commanderId, mode, powerLevel, useCollectionOnly, archetypeHint } = req.body;
  const candidates = await buildCandidatePool({ commanderId, useCollectionOnly, userId });
  const userPrompt = buildUserPrompt({ candidates, mode, powerLevel, archetypeHint });

  const response = await client.messages.create({
    model: mode === 'retune' ? 'claude-sonnet-4-6' : 'claude-opus-4-8',
    max_tokens: 4096,
    system: [
      { type: 'text', text: SYSTEM_PROMPT, cache_control: { type: 'ephemeral' } },
    ],
    messages: [{ role: 'user', content: userPrompt }],
  });

  const parsed = parseStructuredResponse(response, candidates);
  await incrementBudget(userId);
  await cacheResponse(hash, parsed);
  return res.status(200).json({ recommended: parsed, budget_remaining: 20 - (newCount) });
}
```

## Data Model

### Supabase Schema (counterflux.* — huxley project)

**New tables:**

| Table | Purpose | Key columns |
|---|---|---|
| `counterflux.deckgen_cache` | Hash-keyed response cache, 7d TTL | `hash` (text PK), `response` (jsonb), `fetched_at` (timestamptz), `user_id` (uuid FK) |
| `counterflux.deckgen_recommendations` | Cron-generated upgrade/retune recommendations | `id` (uuid PK), `deck_id` (uuid FK), `type` (text — 'upgrade' or 'retune'), `recommendations` (jsonb), `generated_at` (timestamptz), `dismissed` (bool), `dismissed_at` (timestamptz), `user_id` (uuid FK) |

**Profile extensions** (existing `counterflux.profile` table):

| Column | Type | Default | Purpose |
|---|---|---|---|
| `deckgen_generations_today` | `int` | `0` | Counter incremented per /api/deckgen call |
| `deckgen_last_reset` | `date` | `null` | Last UTC date when the counter was reset to 0 |

**RLS model:** standard pattern from v1.0–v1.2.

```sql
ALTER TABLE counterflux.deckgen_cache ENABLE ROW LEVEL SECURITY;
CREATE POLICY "users see own deckgen cache"
  ON counterflux.deckgen_cache FOR SELECT
  USING (auth.uid() = user_id);
CREATE POLICY "users modify own deckgen cache"
  ON counterflux.deckgen_cache FOR ALL
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

ALTER TABLE counterflux.deckgen_recommendations ENABLE ROW LEVEL SECURITY;
CREATE POLICY "users see own recommendations"
  ON counterflux.deckgen_recommendations FOR SELECT
  USING (auth.uid() = user_id);
CREATE POLICY "users modify own recommendations"
  ON counterflux.deckgen_recommendations FOR ALL
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);
```

The cron uses service-role and bypasses RLS for INSERTS into `deckgen_recommendations` (explicit service-role context, not a user JWT).

## Privacy & Data Handling

- **Anthropic API key** lives in Vercel env var (`ANTHROPIC_API_KEY`). Never bundled, never sent to the browser, never logged.
- **Collection isolation:** the user's collection is queried via their own Supabase JWT (RLS-enforced). Cards in the collection are used as a server-side FILTER on the EDHREC candidate pool — the full collection list never reaches Anthropic. Claude only sees the post-filter candidate list (~200 cards max).
- **Prompt-caching is ephemeral.** Anthropic's cache TTL is 5 minutes per their published API behaviour. No long-term data retention on Anthropic's side beyond standard inference logs.
- **deckgen_recommendations rows** are user-scoped via RLS. The cron uses service-role for cross-user scans but writes per-user rows that the user's own JWT can subsequently see.
- **No prompt or response logging on Counterflux.** Vercel Function logs capture errors only. No telemetry on what cards the user generated or accepted.
- **User can clear deckgen state.** `deckgen_cache` rows expire at 7d TTL. `deckgen_recommendations` rows are dismissed (soft-delete) on user action; hard-deleted at 30d via a cleanup pass.

## Edge Cases & Error Handling

| Scenario | Handling |
|---|---|
| User exceeds 20/day budget | `429` from `/api/deckgen` with toast: "Mila needs a break — brewing limit resets at midnight UTC. Try a retune (cheaper) or wait." |
| Anthropic API timeout (> 30s) | One retry with 30s timeout, then `502` + toast: "Mila's deep in thought — try again in a moment." |
| Claude returns invalid JSON | Re-prompt once with stricter schema instruction. If still invalid, fail-soft to `502` + toast: "Mila got distracted by a squirrel — try again." |
| EDHREC candidate pool < 50 cards | Toast: "Not enough EDHREC data for this commander yet — try again in 24h or pick a more-played commander." |
| `useCollectionOnly = true` but collection has < 60 cards in colour identity | Modal warning before submit: "Your collection has 47 cards in these colours — Mila will struggle. Switch off 'Use only my collection' to brew with the full pool?" |
| Cron runs against a deleted deck | Skip silently. `deck_id` FK uses `ON DELETE CASCADE`, so stale `deckgen_recommendations` rows clean themselves up. |
| User edits the deck mid-review | Review screen shows banner: "Deck has changed since recommendations were generated. Refresh recommendations?" with refresh button. Existing approve toggles are preserved. |
| Concurrent brew requests for the same hash | Second call returns cached response if within 7d TTL. Otherwise the second call is idempotent — same hash, same response. |
| Anthropic API key missing in Vercel env | `/api/deckgen` returns `500` with dev-mode log message linking to the runbook. Production: silently fails-closed with toast. |
| Daily budget reset race (two concurrent calls at UTC midnight) | Lazy reset — if `last_reset < today_utc`, reset counter to 0 BEFORE the increment. Atomic via Postgres `UPDATE ... RETURNING`. |
| User dismisses an upgrade recommendation, then the same card lands in a future cron | Cron skips recommendations matching previously-dismissed (deck_id, scryfall_id) pairs from the last 30 days. |
| Claude recommends a card not in the candidate pool (hallucination) | Server-side validation rejects the card from the response before returning. If > 30% of recommendations are rejected, fail-soft to `502` + retry with stricter prompt. |
| User has no Anthropic budget left but tries upgrade review | Toast: "Your daily limit reset at midnight UTC — review cached recommendations for now." (Cached recommendations from prior cron runs still work — they don't consume new budget.) |
| Sonnet retune returns 20+ swaps (over-aggressive) | Server-side cap at 15 swaps per response. Claude is prompted to stay within range; cap is defensive. |

## Cost Model

Estimated per-call costs with prompt-caching engaged (system prompt ~3K tokens, qualifies for ephemeral cache):

| Call type | Model | Input tokens (cold / warm) | Output tokens | Cold cost | Warm cost |
|---|---|---|---|---|---|
| Full brew (99 cards) | Opus 4.8 | ~8K / ~2K | ~2K | ~$0.12 | ~$0.04 |
| Fill mode (30 cards) | Opus 4.8 | ~6K / ~2K | ~1K | ~$0.08 | ~$0.03 |
| Upgrade swap-out (10 cards) | Opus 4.8 | ~5K / ~2K | ~1K | ~$0.06 | ~$0.025 |
| Retune (10 swaps) | Sonnet 4.6 | ~3K / ~1K | ~1K | ~$0.015 | ~$0.005 |

**Daily cost estimates:**

- James's typical use: 2 brews + 1 retune + ~5 cron-generated upgrades = ~$0.25-0.50/day
- Worst-case (hitting 20-call cap): ~$1.50-2/day
- Cron-only days (no manual brews): ~$0.20/day

**Cache savings:** the prompt cache cuts input cost by ~70% on warm calls. After the first week with regular use, expect > 40% cache hit rate on system prompt loads.

**Budget rationale:** the 20/day cap is ~50× James's expected usage. "Generous" per the user brief while still bounding catastrophic abuse (e.g. a runaway client-side loop). The cap is per-user, so a household with two synced accounts gets 40/day combined.

## Assumptions

Where the existing codebase (`src/`, `.planning/`, prior commits) was authoritative, it was used directly. Where it implies but does not state, the following inferences were made:

1. **Prompt-cache savings of ~70%.** Inferred from Anthropic SDK documentation for ephemeral prompt-caching. May vary with actual usage patterns and Anthropic's evolving cache hit logic.

2. **EDHREC top-300 is enough candidate breadth.** Inferred from existing `getCommanderSynergies` behaviour in v1.2 — most decks pull 80-95 of their non-land cards from the top-300 synergy list. Assumption — flag to confirm during Phase 17 implementation.

3. **Anthropic Claude API latency targets (Opus < 30s, Sonnet < 12s).** Inferred from Anthropic's published p95 figures for ~8K input + ~2K output workloads. May need tuning based on real-world Phase 17 measurements.

4. **Hash-based response cache TTL of 7 days is appropriate.** Inferred from EDHREC's data refresh cadence — EDHREC's top-300 doesn't shift meaningfully within a week. Long-running brews may want a shorter TTL for in-development decks; this is tuneable post-ship.

5. **20 generations/day is "generous."** Inferred from James's stated brewing cadence (~3 decks/week). 20/day is ~50× headroom. Flag to confirm.

6. **Vercel Cron daily at 4am UTC.** Speculative — the schedule should be tuned based on actual deployment and observed user activity. Could shift to weekly if cost becomes a concern.

7. **Notification bell extension is straightforward.** Inferred from existing v1.1 Phase 12 patterns. Requires review of `src/components/notification-bell-popover.js` during Phase 19 implementation to confirm the notification schema accommodates the new type.

8. **"Salt" terminology will be re-cast as "Power Level" in the UI.** Inferred from QA finding on 2026-06-07 — Salt was useful as an EDHREC concept but confused users. New copy uses Casual / Focused / Optimized / cEDH. The existing Salt panel may need to be retired or relabelled. Flag to confirm during Phase 18 UI work.

9. **Single-transaction commit is achievable with current Dexie deck_cards schema.** Verified — v1.2's `addAllFromPrecon` already does multi-row deck commits atomically via `db.transaction('rw', ...)`. The same pattern applies here.

10. **Mila branding for the AI persona is the right voice.** Inferred — Mila is the existing Corgi system familiar from v1.0 onwards. Making her the AI face is consistent with current branding and prior decisions (Mila empty states, Mila loading video shipped 2026-06-06).
