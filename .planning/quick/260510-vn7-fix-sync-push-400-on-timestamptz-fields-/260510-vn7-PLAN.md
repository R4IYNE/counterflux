<objective>
Bugfix: `flushQueue()` in `src/services/sync-engine.js` is sending JS Number timestamps (epoch-ms, e.g. `1776555292268`) to Supabase, where `timestamp with time zone` columns reject the value as out-of-range (~year 58 million). Every `deck_cards` mutation since v1.1 ship has been silently dead-lettering to `sync_conflicts` — the user has 90 accumulated failures and cloud holds 0 deck_cards rows.

The fix is a small conversion seam at the upsert call site (~line 421): walk each row before upsert, and if a known timestamptz key carries a Number value, convert it to an ISO-8601 string via `new Date(v).toISOString()`. Whitelist by column name across all six synced tables. Hooks at lines 220 / 243 are deliberately NOT touched — they continue to stamp Number values into local Dexie (consumed by the LWW resolver via `_toTs`, which is already tolerant of both shapes per the read in sync-pull.js:73-78). Migrating local Dexie data to ISO strings is out of scope for this hot-fix and tracked as a v1.3 SEED-006 candidate.

Purpose: unblock cloud sync for deck_cards and any other synced row that carries a Number timestamp in its payload. Once shipped, the user's "Retry All" path drains the 90 backed-up conflicts.

Output:
- 1 new RED-then-GREEN regression test in `tests/sync-engine-push.test.js` (extends the existing 'flushQueue pipeline' describe block).
- ~15 LoC of new code in `src/services/sync-engine.js`: a private `_isoStampTimestamps(rows)` helper + one call from the upsert path.
</objective>

```javascript
function _toTs(v) {
  if (v == null) return 0;
  if (typeof v === 'number') return v;
  if (typeof v === 'string') {
    const ms = Date.parse(v);
    return Number.isFinite(ms) ? ms : 0;
  }
  return 0;
}
// _toTs is consumed by resolveLWW for tie-break — already tolerates BOTH Number and ISO,
// so the LWW resolver is unaffected by what shape lives in local Dexie. The push-side
// conversion happens AT the Supabase boundary; local Dexie keeps Number values.
```

    ```javascript
    // ---------------------------------------------------------------------------
    // Number → ISO timestamp conversion (vn7 hot-fix)
    // ---------------------------------------------------------------------------
    // Postgres `timestamp with time zone` cannot parse a raw integer like
    // 1776555292268 — it interprets ms-since-epoch as ~year 58 million and
    // rejects with `date/time field value out of range`. The Dexie creating /
    // updating hooks (sync-engine.js:220, :243) intentionally stamp `updated_at`
    // as a JS Number for local-side LWW math (consumed by sync-pull.js _toTs,
    // which is tolerant of both shapes). At the Supabase boundary we serialise
    // to ISO so PostgREST + Postgres accept the value.
    //
    // Whitelist is name-based across all 6 synced tables — any future timestamptz
    // column added under one of these names is auto-covered. Migrating local
    // Dexie data to ISO strings is intentionally OUT OF SCOPE (tracked as v1.3
    // SEED-006 candidate). Non-finite Numbers are left untouched so Postgres
    // rejects them and the real bug surfaces rather than being masked.
    //
    // Mutates each row in place (safe — caller's `{ ...e.payload, user_id: ... }`
    // spread produces a fresh object on each call to flushQueue). Returns the
    // same array reference for caller fluency.
    const TIMESTAMPTZ_COLUMNS = [
      'updated_at', 'synced_at', 'deleted_at', 'added_at',
      'created_at', 'started_at', 'ended_at', 'last_alerted_at'
    ];

    function _isoStampTimestamps(rows) {
      for (const row of rows) {
        if (!row) continue;
        for (const col of TIMESTAMPTZ_COLUMNS) {
          const v = row[col];
          if (typeof v === 'number' && Number.isFinite(v)) {
            row[col] = new Date(v).toISOString();
          }
        }
      }
      return rows;
    }
    ```
