# Quick Task 260510-w54: Fix flushQueue Re-Entrancy Bug Causing Postgres Deadlocks Summary

**One-liner:** Module-level `_flushing` boolean + try/finally wrap + finally-block follow-up flush in `flushQueue()` eliminates the Postgres AccessExclusiveLock deadlocks observed during bulk RETRY ALL of dead-lettered sync_conflicts.

## Context

This is the second half of the bulk-RETRY-ALL recovery story started by quick task **260510-vn7** (Number → ISO timestamp conversion at the Supabase upsert seam). The vn7 fix unblocked the HTTP 400 timestamptz rejection symptom; once payloads were syntactically valid, the residual blocker surfaced — concurrent `flushQueue()` invocations from the bulk-retry handler were racing on the same `sync_queue` rows, both upserting overlapping row IDs to Postgres, and triggering tuple-level deadlocks.

User context (from supabase-huxley MCP postgres logs, 2026-05-10): bulk RETRY ALL of 90 `sync_conflicts` only landed 6 `deck_cards` rows — the other 84 re-dead-lettered because ~25 parallel processes deadlocked at tuple `(10,25)` of relation `46471` (the `counterflux.deck_cards` table). With this fix, a single in-flight flush now serialises the entire backlog.

## The 4 Surgical Edits to `src/services/sync-engine.js`

Anchor line numbers are post-edit (worktree commit `e3e9ecd`).

### Edit 1 — Module-level `_flushing` declaration (line 73)
Added immediately after `_suppressHooks = 0` (line 59), with a 14-line comment explaining the deadlock root cause and design rationale. A plain boolean is sufficient because `flushQueue` is the only setter and there is no nesting concern.

### Edit 2 — Re-entrancy gate inside `flushQueue()` (line 428)
Placed AFTER the three existing early-returns (auth, online, currentUserId) so harmless no-op calls aren't gated. The gate sets `_flushing = true` and is released exclusively by the finally block.

```javascript
if (_flushing) return;
_flushing = true;
```

### Edit 3 — try/finally wrap (try opens line 432, finally line 599)
Wraps the entire existing flush body — from `// PITFALLS §7: only flush entries...` through to the success/remaining branch. Pure re-indentation inside the try (zero logic changes); all existing internal `return;` statements (queue.length === 0, deadLetter return, transient retry path) correctly hit the finally on exit.

### Edit 4 — finally block (line 599) + `__resetSyncEngineForTests` reset (line 735)
The finally block releases `_flushing = false`, then unfiltered-counts `db.sync_queue` and calls `scheduleFlush(0)` if any rows remain. The unfiltered count is intentional — `scheduleFlush(0) → flushQueue()` re-applies the `user_id` filter at the top, so a follow-up flush with no work is a free no-op for the cross-user case. A `try/catch` around the count keeps a Dexie hiccup from masking the original error path. The test-only reset adds `_flushing = false` to ensure isolation between tests.

## The 2 New Regression Tests

Both appended to the existing `describe('sync-engine push: flushQueue pipeline', () => { ... })` block in `tests/sync-engine-push.test.js`.

### Test A — "concurrent flushQueue() calls only fire one upsert (w54 re-entrancy guard)"
- Seeds `sync_queue` with one `decks` put row.
- Replaces `supabaseStub.schema` for the test scope with a delay-resolving upsert (~30ms via `setTimeout`).
- Fires `await Promise.all([flushQueue(), flushQueue()])`.
- Asserts `upsertCalls.filter(c => c.table === 'decks').length === 1` and `db.sync_queue.count() === 0`.
- RED state confirmed: pre-fix value was 2 (both parallel calls upserted).

### Test B — "new sync_queue entry added during flush triggers a follow-up flush (w54 mid-flight drain)"
- Seeds row 1, kicks off `flushQueue()` WITHOUT awaiting (delay-resolving upsert).
- Sleeps 5ms, adds row 2 mid-flight, awaits the original flush, sleeps 80ms for the scheduleFlush(0) timer + its delay-resolving upsert to settle.
- Asserts `upsertCalls.filter(c => c.table === 'decks').length === 2` and `db.sync_queue.count() === 0`.
- RED state confirmed: pre-fix value was 1 (row 2 stranded in queue).

The per-test `supabaseStub.schema` replacement (with `try { ... } finally { restore }`) keeps the file's shared mock harness untouched for the other 19 tests.

### Delay-Resolving Upsert Pattern
```javascript
const originalSchema = supabaseStub.schema;
supabaseStub.schema = vi.fn((_schemaName) => ({
  from: vi.fn((tableName) => ({
    upsert: vi.fn(async (rows) => {
      upsertCalls.push({ table: tableName, rows });
      await new Promise(r => setTimeout(r, 30));
      return { error: null };
    }),
    delete: vi.fn(() => ({ eq: vi.fn(async () => ({ error: null })) }))
  }))
}));
try { /* test body */ } finally { supabaseStub.schema = originalSchema; }
```

## Seeds Raised

**SEED-007 candidate** (observed during implementation, not raised in this commit — leave for `/gsd:new-milestone` v1.3 scoping discussion):

> `scheduleFlush` refactor — fold the `_flushTimer` single-shot debounce semantics into `flushQueue` itself, eliminating two separate guards (`_flushTimer` and `_flushing`) that share the same conceptual goal of "only one flush at a time, with backpressure." Today's design has `_flushTimer` for "don't fire repeatedly during a 500ms burst" and `_flushing` for "don't run two flushes in parallel" — could collapse to a single state machine. Cost is a refactor that touches `scheduleFlush`, `_scheduleRetry`, `initSyncEngine`, and `teardownSyncEngine`. Trigger: when a third concurrency concern surfaces, OR when the next sync-engine bug investigation makes the dual-guard hard to reason about.
