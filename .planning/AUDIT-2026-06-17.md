## Manual / backend findings (verified by hand via Supabase MCP + code read)

There is no household ID — it only checks "row owner is in shared_users AND caller is in shared_users". Safe only while exactly ONE household exists; adding any second person/group to `shared_users` merges ALL collections/decks/games with zero tenant isolation. (Pairs with P2-H2/M2: reconciliation re-tags foreign local rows to the signing-in user and pushes them to the cloud.)  Files: Supabase `counterflux.is_household_member`, all `counterflux.*` policies.
- **[LOW] `anon` has EXECUTE on `is_household_member`** — `/rest/v1/rpc/is_household_member?check_uid=<uuid>` is a membership-probe oracle for unauthenticated callers. (Anon still cannot read tables: `is_household_member(null)` is false.) Revoke EXECUTE from anon.
- **[MEDIUM] No PWA service worker or web manifest** despite the "offline PWA" product claim. Confirmed absent (no SW registration, no VitePWA, no manifest link). "Works offline" holds only for already-loaded Dexie data; a cold reload while offline serves nothing, and the app is not installable / has no update mechanism.
- **[BACKEND/perf] ~18 `counterflux` RLS policies re-evaluate `auth.uid()`/`is_household_member()` per row** — wrap as `(select auth.uid())` to evaluate once per query.
- **[BACKEND/perf] Every `counterflux` table has TWO permissive SELECT policies** ("household sees X" + "household modifies X" with cmd=ALL) that both run on every SELECT — consolidate.
- **[BACKEND/perf] `counterflux.deck_cards.deck_id` FK has no covering index** — add one (also speeds the sync push).
- **[BACKEND/security] Supabase leaked-password (HIBP) protection is DISABLED** — enable it (one toggle).
- **[BACKEND/note] `is_household_member` `search_path` IS correctly set to `''`** — the advisor's blanket "20 mutable search_path functions" does NOT apply to this counterflux function (those are other apps in the shared project).

## HIGH (11)


### H1. Deck import ignores card quantity — every line imports as a single copy  

`bug` · P1 · confidence 0.95  

**Files:** src/components/deck-import-modal.js, src/stores/deck.js  

**Evidence:** deck-import-modal.js lines 162-169 iterate resolved entries and call `await store?.addCard(entry.scryfallId, [])` exactly once per entry, discarding `entry.qty` entirely. `store.addCard` (deck.js lines 147-209) only ever adds quantity 1 (or +1 for an existing basic/any-number card). So importing a list containing e.g. `36 Mountain`, `4 Lightning Bolt` (60-card decks), or any non-singleton format adds just ONE copy of each. The parser correctly captures qty (deck-import.js parseCardLine returns `{qty, name}`), but it is thrown away at the add step.  

**Impact:** Imported decks are silently wrong: basic-land counts collapse to 1, and any 60-card constructed import (Standard/Modern/Legacy/Vintage/Pauper — all offered in the ritual modal) loses all 2-4x playsets. The user gets a 'success' toast claiming N cards resolved while the deck is structurally broken, with no indication quantities were dropped.  

**Fix:** Honor `entry.qty`: either loop `entry.qty` times calling addCard, or (better) add a quantity-aware add path. For basic lands / any-number cards use updateCardQuantity to set the parsed qty directly; for singleton commander decks cap at 1 but still import the right basics count.  


### H2. Stored XSS via deck name in dashboard "Daily Insight" panel  

`security` · P1 · confidence 0.95  

**Files:** src/screens/epic-experiment.js, src/utils/insight-engine.js  

**Evidence:** insight-engine.js:84 builds the message string with raw user data: `message: `Swap in ${candidate.suggestedCard} for your ${candidate.deckName} deck — +${synergyPercent}% synergy on EDHREC`` where candidate.deckName = deck.name (insight-engine.js:59, the user-typed deck name) and candidate.suggestedCard = suggestion.name from the EDHREC cache (external API). That message is then injected unescaped at epic-experiment.js:955 inside the loadInsight() template: `<p ...>${insight.message}</p>` assigned via `content.innerHTML = ...` (epic-experiment.js:947). A deck named e.g. `<img src=x onerror=alert(document.cookie)>` (set via the Rename Deck prompt in deck-landing-context-menu.js:90 or the Brew ritual) renders on the dashboard and executes. Note the rest of the codebase escapes this pattern with a proper `_escape()` helper (sync-errors-modal.js:51-53, settings-modal.js, first-sign-in-prompt.js, sync-pull-splash.js) and uses x-text/textContent everywhere else for deck names — this sink simply missed it.  

**Impact:** Arbitrary JS execution in the app's origin whenever the dashboard renders the daily insight for a deck whose name (or the EDHREC suggested card name) contains markup. The Supabase session token lives in localStorage (auth.js hasPriorSession reads sb-*-auth-token), so this is exfiltratable — full account/sync compromise. It is self-XSS in solo use, but deck rows sync via Supabase, so in any shared-account/household scenario a malicious deck name persisted by one device executes on another.  

**Fix:** Escape the interpolated values before they reach innerHTML. Simplest: build the insight panel imperatively (textContent) like the adjacent price-alerts (epic-experiment.js:1007-1010) and upcoming-releases (1108-1117) panels already do; or apply the existing `_escape()` helper to insight.message at the epic-experiment.js:955 sink (and ideally inside generateDailyInsight when composing the string).  


### H3. Stored XSS: deck name interpolated raw into delete-confirmation modal innerHTML  

`security` · P2 · confidence 0.92  

**Files:** src/components/delete-deck-modal.js  

**Evidence:** delete-deck-modal.js line 35 builds the modal via `overlay.innerHTML = \`...\` <h3 ...>Delete "${deckName}"?</h3> ...\`` with NO escaping. `deckName` is the user-authored deck name: openDeleteDeckModal(deckId, deckName) is called with `deck.name` from both deck-editor.js:69 (`openDeleteDeckModal(deck.id, deck.name, {...})`) and deck-landing-context-menu.js:119 (`openDeleteDeckModal(deck.id, deck.name)`). Deck names are user-controlled (created/renamed via the ritual modal and the 'Rename Deck' prompt in deck-landing-context-menu.js:90) and are synced through Supabase. ### H4. Daily LLM budget enforcement is a non-atomic read-then-write — concurrent requests bypass the quota (paid-LLM abuse)  

`security` · P1 · confidence 0.9  

**Files:** api/_deckgen-shared.js, supabase/migrations/20260607_counterflux_deckgen.sql  

**Evidence:** assertAndIncrementBudget (_deckgen-shared.js:86-146) does SELECT current count (lines 91-95), computes usedBefore, checks `usedBefore >= cap` (line 110), then UPDATEs the new count (lines 135-138). This is a classic TOCTOU race: two (or N) requests carrying the same valid JWT fired concurrently each read the same pre-increment count, each pass the cap check, and each proceed to call Claude — then both write back usedBefore+1. The DB-side check is not conditional (no `WHERE count < cap`, no atomic UPDATE...RETURNING, no RPC). The migration comment at 20260607_counterflux_deckgen.sql:79 even claims an 'atomic UPDATE RETURNING pattern', but the shipped code does not implement it. Verified there is no server-side RPC for the increment (grep of supabase/migrations for rpc/increment/FOR UPDATE found none). Both /api/deckgen (deckgen.js:162) and /api/deckgen-chat (deckgen-chat.js:103) use this same helper.  

**Impact:** The per-user daily cap (20 brews / 60 chats) protecting a paid Opus/Sonnet endpoint is bypassable by a single authenticated user firing parallel requests. An attacker (or a buggy client retry storm) can drive Anthropic spend well past the intended ceiling — the cap is the only cost-control on the most expensive endpoint in the app. Bounded by needing a valid account, but any signed-in user can do it.  

**Fix:** Make the increment atomic in Postgres: either a `SECURITY DEFINER` RPC that does `UPDATE profile SET count = count + 1 WHERE user_id = auth.uid() AND count < cap RETURNING count` (returns null/0 rows when over cap), or a single conditional UPDATE that the API treats as 'over budget' when it affects 0 rows. The lazy daily-reset can be folded into the same statement with a CASE on the reset column. This closes the race and matches the behaviour the migration comment already claims.  


### H5. Color identity, singleton, and banlist are not validated on deck import — illegal lists are silently accepted  

`missing-feature` · P1 · confidence 0.9  

**Files:** src/components/deck-import-modal.js, src/services/deck-import.js  

**Evidence:** deck-import-modal.js:162-169 loops over every resolved card and calls `await store?.addCard(entry.scryfallId, [])`, discarding the return value. For commander decks addCard returns `{ warning: true, message: '... singleton format' }` on a duplicate (deck.js:174), but the import swallows it, so a pasted list with duplicate non-basics is silently truncated to one copy with no notice. The commander's color identity is set from the imported commander (line 166) but no imported card in `parsed.main` is ever checked against it, and there is no banlist check. resolveDecklist (deck-import.js) also blind-picks `cards[0]` as the match (line 166) with no verification the resolved card is even legal in the target format.  

**Impact:** Importing a Moxfield/Archidekt/Arena list that is illegal (off-color cards, banned cards, or a deck the user tweaked) produces a deck Counterflux presents as fine. Singleton dupes vanish without warning, so the imported deck silently differs from the source. Users importing across platforms — the explicit use case in the import service header — get a misleading result.  

**Fix:** After resolution, run the same legality service against the resolved list and show a summary (off-color N, banned N, singleton-collapsed N) alongside the existing 'could not be resolved' list before committing.  


### H6. reconciliation classifyState and _enqueueAllLocalRows ignore row ownership — any pre-existing local rows are claimed by whoever signs in  

`data-integrity` · P2 · confidence 0.88  

**Files:** src/services/sync-reconciliation.js  

**Evidence:** RECONCILIATION_TABLES counts use unfiltered `db.table(t).count()` (lines 43-45) and SYNCABLE_TABLES enqueue uses unfiltered `db.table(t).toArray()` (lines 295-297) inside _enqueueAllLocalRows(). Both paths assign `user_id: _currentUserId()` to every row regardless of the row's stored user_id. The per-user one-shot guard (_isReconciled / sync_reconciled_at:<userId>, lines 121-124) only suppresses the modal; it does not scope which rows get pushed. So even in the populated-populated MERGE/KEEP_LOCAL branches, foreign rows still get re-tagged and pushed.  

**Impact:** This is the mechanism behind the cross-account contamination finding and also means the reconciliation 'how much local vs cloud data' counts shown to the user in the lockdown modal mix in a prior user's rows, misrepresenting what is being merged/overwritten.  

**Fix:** Scope all reconciliation reads and enqueues by user_id (null-or-current only). Treat rows owned by a different user_id as not-this-user's data: exclude from counts, never push, and clear them on sign-out.  


### H7. Table view is not virtualized — renders every collection entry, freezing the main thread on large collections  

`performance` · P1 · confidence 0.85  

**Files:** src/components/table-view.js  

**Evidence:** table-view.js:87 iterates the FULL sorted list with no windowing: `<template x-for="(entry, idx) in items" :key="entry.id || idx">` where `items` getter (line 12) returns `$store.collection.sorted` — every per-printing entry. The gallery (grouped-view.js) was recently windowed with an IntersectionObserver (visibleCount, line 26-48) and the legacy gallery used the virtual scroller, but the TABLE view builds a `<tr>` for every entry. A collection with thousands of printings mounts thousands of Alpine-reactive table rows on tab switch. **Impact:** Switching to the TABLE view on a large synced collection mounts one reactive <tr> per printing, producing a multi-second main-thread freeze and the same gotrue/Realtime starvation the grouped-grid windowing was introduced to fix. Table is the one collection view that still has the un-windowed problem.  

**Fix:** Apply the same incremental-render/IntersectionObserver windowing used in grouped-view.js (visibleCount + sentinel) to the table tbody, or route the table through createVirtualScroller in list mode (columns:1).  


### H8. Removing a card then triggering loadDeck within 10s resurrects the removed card  

`bug` · P1 · confidence 0.85  

**Files:** src/stores/deck.js, src/stores/undo.js  

**Evidence:** removeCard (deck.js lines 236-262) removes the card from `activeCards` optimistically but defers the actual `db.deck_cards.delete` into the undo commitFn, which only runs after the 10s timer in undo.js (lines 10-18). Meanwhile any other deck mutation re-reads the DB: addCard calls `await this.loadDeck(deckId)` (line 207), updateCardQuantity calls loadDeck (line 232), the basic-land steppers call removeCard/updateCardQuantity, and printing-swap calls loadDeck (deck-card-tile.js line 448). loadDeck (lines 90-115) rebuilds activeCards from `db.deck_cards`, where the 'removed' row still physically exists for up to 10s.  

**Impact:** Reproducible data-integrity/UX bug: remove card A, then add card B (or +/- a basic, or change a printing) before the 10s undo window elapses, and card A reappears in the deck. The user must remove it again. Counts, analytics, and exports are wrong during the window.  

**Fix:** Delete the row from Dexie immediately (synchronously with the optimistic UI removal) and make the undo restoreFn re-add it; or have loadDeck filter out IDs that are pending deferred-delete in the undo stack. The deck delete path (deleteDeck) already deletes-on-commit but is safe only because the whole deck leaves the UI — single-card remove is not.  


### H9. deck_cards composite-key atomic merge is unreachable — duplicate (deck_id, scryfall_id) rows accumulate on every cross-device merge  

`data-integrity` · P1 · confidence 0.8  

**Files:** src/services/sync-pull.js, src/services/sync-realtime.js, src/db/schema.js  

**Evidence:** The merge path looks up the local row by UUID PK only: sync-pull.js:320 `const local = await db.table(tableName).get(r.id)` and sync-realtime.js:150 the same. resolveDeckCardConflict (sync-pull.js:122-139) is the documented composite-merge resolver, but _mergeIncomingRows/_applyIncomingRow only call it AFTER a local row was found by id (line 333/163), and resolveDeckCardConflict itself returns early when `local.id === remote.id` (line 123). The composite conflict it is designed for — same (deck_id, scryfall_id) but DIFFERENT UUIDs across devices (exactly what the v6 migration's `crypto.randomUUID()` produces independently per device) — means `get(r.id)` returns null, so line 321-322 just `add(incoming)`. The schema index `[deck_id+scryfall_id]` is non-unique (no `&` prefix, schema.js:313), so the duplicate add succeeds.  

**Impact:** Whenever the same card is added to the same deck on two devices/tabs offline, sync produces TWO deck_cards rows for one logical card — inflated deck counts, double quantities, broken deckbuilding math. The intended dedup/merge never runs.  

**Fix:** In the merge functions, before `add`, look up by composite when tableName==='deck_cards': `db.deck_cards.where('[deck_id+scryfall_id]').equals([incoming.deck_id, incoming.scryfall_id]).first()` and route a composite hit through resolveDeckCardConflict. Consider making the composite index unique.  


### H10. LWW conflict resolver _toTs() returns 0 for numeric-string timestamps → silent loss of local edits  

`data-integrity` · P1 · confidence 0.8  

**Files:** src/services/sync-pull.js  

**Evidence:** sync-pull.js:73-81 `_toTs` only handles `typeof === 'number'` and ISO strings via `new Date(v).getTime()`. For a numeric-string timestamp like "1777662820234" (which utils/timestamps.js header explicitly documents exists: "some values round-tripped as numeric STRINGS"), `new Date('1777662820234').getTime()` returns NaN, so `_toTs` returns 0. In `resolveLWW` (lines 99-105) the local row's updated_at then evaluates to ts=0, so `ru > lu` is true for almost any remote row and the local row LOSES every conflict. tsToMs() in timestamps.js handles this correctly (line 30: `/^\d+$/.test(v)` → Number(v)) but _toTs was never aligned with it.  

**Impact:** Any locally-modified row whose updated_at was stamped/round-tripped as a numeric string is treated as epoch 0 during sync pull, so the cloud copy always wins the last-write-wins comparison. Genuine local edits (e.g. a quantity bump or a deck change made offline) are silently overwritten by stale cloud data — sync divergence / data loss with no conflict surfaced.  

**Fix:** Replace `_toTs` with the shared `tsToMs` from utils/timestamps.js (it already handles number, ISO string, AND numeric-string forms), or add the `/^\d+$/.test(v) → Number(v)` branch to `_toTs` so the two timestamp coercers agree.  


### H11. incrementalPull cursor uses client wall-clock Date.now() against server updated_at — clock skew silently drops or re-pulls rows  

`data-integrity` · P1 · confidence 0.75  

**Files:** src/services/sync-pull.js  

**Evidence:** incrementalPull sets the cursor from the local clock: sync-pull.js:300 `await db.meta.put({ key: LAST_PULLED_KEY, value: Date.now() })`, and bulkPull:266 seeds it the same way. The query filters on the SERVER timestamp: line 291 `const sinceIso = new Date(since).toISOString()`, line 294 `.gt('updated_at', sinceIso)` where updated_at is server-written (the Supabase columns default to server now()). If the client clock is ahead of the server (common by several seconds), the cursor is set to a future server time, so the next `.gt()` window MISSES rows another device wrote in the gap — a permanent lost-update window until something forces a full re-pull. If the client clock is behind, every poll re-pulls overlapping rows (extra work, and feeds the duplicate-add bug above).  

**Impact:** Silent sync divergence proportional to clock skew. Remote updates within the skew window never land locally; the 60s backstop is supposed to be the safety net and instead has a hole. Realtime masks it when connected, but offline-then-reconnect relies entirely on this cursor.  

**Fix:** Drive the cursor from server time, not Date.now(): use `max(updated_at)` returned by the pull batch as the next cursor (with a small overlap and id-based dedup), or fetch the server clock. Never compare a client-generated cursor against server-generated timestamps.

### M1. signOut() does not clear any Dexie/IndexedDB data — prior user's library persists for the next account on a shared device  

`security` · P2 · confidence 0.97  

**Files:** src/stores/auth.js  

**Evidence:** auth.js signOut() (lines 158-180) calls supabase.auth.signOut() and then only nulls this.session/this.user/this.status. The inline comment at lines 169-174 explicitly states sign-out 'no longer clears anything' (the per-user sync_reconciled_at keys are intentionally left). Gate the next sign-in's reconciliation on a clean local state.  


### M2. No deck legality validation: banlist, color-identity, and singleton are never enforced on the built deck  

`missing-feature` · P1 · confidence 0.95  

**Files:** src/stores/deck.js, src/components/deck-centre-panel.js, src/services/deck-diagnostics.js  

**Evidence:** There is no legality/banlist module anywhere in src/ — `grep banned|banlist` only hits the AI candidate pre-filter (src/services/deckgen-candidates.js:144), never the user's hand-built deck. ### M3. Cross-account data contamination: signing in as User B pushes User A's leftover local rows to the cloud under User B's user_id  

`data-integrity` · P2 · confidence 0.93  

**Files:** src/services/sync-reconciliation.js, src/services/sync-engine.js  

**Evidence:** Because signOut() leaves User A's rows in Dexie (finding above), the next sign-in's reconcile() treats them as User B's local data. classifyState() (sync-reconciliation.js:42-46) counts local rows with `db.table(t).count()` — there is NO `.where('user_id')` filter, so User A's rows (user_id:null or user_id:A) inflate localCounts and mark the state 'populated'. In the populated-empty branch (line 172-177) reconcile() calls `_enqueueAllLocalRows()`, which (lines 291-309) iterates EVERY local row and enqueues it with `user_id: _currentUserId()` = User B. flushQueue() then upserts each row with `{ ...e.payload, user_id: currentUserId }` (sync-engine.js:524) — the spread-then-stamp deliberately OVERWRITES the payload's original user_id (comment at lines 494-496 confirms 'the client is the authority on user_id at push time'). Net effect: User A's collection/decks/games are written to Supabase tagged as belonging to User B. The same overwrite happens in handleKeepLocal() (line 237) and handleMergeEverything() (push side). Nothing in the push path filters local rows by the row's own user_id before re-tagging them to the current user.  

**Impact:** User A's private library is silently re-attributed to User B's account in the cloud and (via the global household RLS) becomes part of the shared dataset under B's identity. This is permanent cloud data corruption / cross-account ownership transfer, not just a local leak. Combined with the global household RLS already flagged, A's data is now durably exfiltrated under B.  

**Fix:** Reconciliation and push must be scoped to the authenticated user. (1) Clear local user-scoped tables on signOut (root fix). (2) Defensively, in classifyState()/_enqueueAllLocalRows()/flushQueue(), only consider/enqueue/push rows whose existing user_id is null or equals the current user_id; never blanket-overwrite a non-null, non-matching user_id onto a foreign row. Rows belonging to a different user_id should be discarded locally rather than re-stamped and pushed.

### M5. No account-deletion or local-data-wipe path exists anywhere in the app  

`compliance` · P2 · confidence 0.9  

**Files:** src/stores/auth.js, src/services/sync-engine.js  

**Evidence:** A full grep for db.<table>.clear / .delete() / 'delete account' / deleteAccount / wipe / clearLocal / indexedDB.deleteDatabase / db.delete() across src returns only: sync-engine.js hard-delete safety-net + per-row cloud delete during flush, and sync-reconciliation.js handleKeepLocal (cloud wipe) / handleKeepCloud (local-table clear during reconciliation).
